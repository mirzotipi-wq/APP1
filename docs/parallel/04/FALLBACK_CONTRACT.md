## Ownership and normal startup

The actor serializes its synchronous render method, backend factory, validation, rendering and cache operations. There is no `await` inside that method. The normal initializer creates a real `MetalStudyRenderer` from `MTLCreateSystemDefaultDevice()`; an eligible, uncached sphere request must complete validation before the actor stores the backend. Validation compares all six canonical fixtures at width 48 with the shipped CPU oracle and checks `StudyParityMetrics.passes`. The parity-only `renderValidationFixture` route retains input and relative-distance checks while bypassing production eligibility; production publication never calls it directly. [Engine][engine], [oracle and packed input][oracle], [canonical metrics][fixtures].

The injected factory is an explicit opt-in seam used by tests; its interface is not compiler-enforced test-only. The default factory actually creates the real backend inside the actor. An injected factory must supply a fresh backend for exclusive actor use, with no externally retained concurrent-use path. Synchronous protocol calls avoid suspension in this work but do not enforce reference exclusivity. Scripted factories and synthetic images demonstrate state handling; they do not demonstrate GPU pixels, cancellation latency or driver-resource release.

## Exact routing and error table

Rows follow the render method's order from entry. A successful cache hit returns before routing or startup, so no later row applies to that call. The cancellation predicate is `Task.isCancelled || additionalCancellation()`: when the task flag is observed true, OR short-circuits and a false extra predicate cannot override it. The reads are not atomic; either flag can change after a false observation. “Admit” means a completed frame reaches the cache after the final cooperative check. CPU rendering can itself throw; then no frame is returned or admitted.

| Stage / event | State after event | Request outcome and cache effect |
|---|---|---|
| Cancellation observed at entry or immediately before cache lookup | Unchanged | Throw `StudyError.cancelled`; no lookup promotion, new frame or admission. |
| Valid matching cache hit | Unchanged | Promote that completed frame to most-recently-used and return its stored image/backend pair. No factory, validation or fresh rendering. |
| Bust request | Unchanged | Use `PortraitStudyRenderer` at `min(requestedWidth,144)`; completed result is CPU. The sphere kernel is never used. Remaining invalid dimensions still fail the CPU constructor. |
| Sphere is outside production Float32 eligibility | Unchanged | Use the Double CPU renderer. Invalid scene, camera or resolution still produces its original renderer error; ineligibility does not make invalid input valid. |
| `unchecked`: factory and all validation succeed, final check is false | `metal(backend)` | Store validated backend, then render this eligible sphere. |
| Startup factory/validation throws `StudyError.cancelled`, `invalidScene`, `invalidCamera`, `invalidResolution`, `invalidEmitter` or `invalidSurface` | `unchecked` | Rethrow that error. No new admission; a later eligible uncached request may retry startup. |
| Startup validation returns, but final cancellation check is true | `unchecked` | Throw `StudyError.cancelled` before storing backend. A later eligible uncached request may retry. |
| Startup factory/validation throws `MetalStudyError.precisionDomain` | `unchecked` | After another cancellation check, attempt CPU for this request; preserve existing cache. A later eligible uncached request retries startup. A hit on a retained CPU result does not retry. |
| Startup throws `StudyError.invalidComputeOutput` or any other error, including Metal unavailable/allocation/command/parity | `cpu` | Select CPU and purge Metal cache entries before the next cancellation check. Then return CPU if successful and still live; otherwise throw cancellation/CPU error. No later startup retry on this engine. |
| `metal`: backend returns an image and final check is false | Same `metal` | Admit/return the image with `.metal`. |
| `metal`: backend throws one of the six non-output `StudyError` cases listed above, or its final check observes cancellation | Same `metal` | Rethrow; preserve validated backend and all previously completed entries. Failed/cancelled request is not admitted. |
| `metal`: backend throws `MetalStudyError.precisionDomain` | Same `metal` | After a cancellation check, attempt CPU for this request. Preserve old Metal and CPU entries; later eligible uncached requests may use the same backend. |
| `metal`: backend throws `StudyError.invalidComputeOutput` or any other error | `cpu` | Purge all engine-cached Metal frames and retain CPU frames. This downgrade precedes observation of concurrent cancellation. Later eligible requests stay CPU. |
| `cpu`: uncached sphere request | `cpu` | Render with CPU; success and final cancellation check control admission. No automatic reset/revalidation exists. |

Once the factory, validation or render callback delivers a confirmed failure, or the submitted Metal command is observed failed, the engine downgrades and purges before its next cancellation check. If that check observes cancellation, the caller receives `StudyError.cancelled` while the actor remains permanently CPU. A request cancelled at entry or before the failing work is invoked confirms no backend failure; merely arming a scripted failure does not cause downgrade. Tests raise cancellation inside the same callback that throws the confirmed failure, then distinguish permanent downgrade with an uncached request and a revisit to the old Metal key.

**Injection error contract:** use `StudyError.cancelled` to model backend cancellation. Production backend cancellation checkpoints currently emit that type. A generic Swift `CancellationError` is not emitted by this backend and currently enters the catch-all failure path, selecting CPU. A consumer's broader cancellation catch does not change this engine behavior. [Engine][engine]; [scripted lifecycle tests][cache-tests].

## Deliberate CPU domain

The width-aware [eligibility predicate][eligibility] accepts only validated sphere/panel input at widths 24–192 divisible by3, with valid camera clearance and bounded relative geometry. Camera distance from subject and every active light's center distance are limited to 20 m; zero-candela lights are exempt from that light-distance condition. Absolute world translation is not the bound: packing subtracts the subject in Double before Float conversion.

Near-field sources, conservative visible-panel bounds, silhouette-sensitive pixel grids and the narrow nonaxial near-vertical camera cone can select CPU. The 1 mm surface margin and distance-scaled silhouette allowance are engineering guards, not proved error bounds for every scene or GPU. A predicate rejection never disables an already validated backend. The mannequin's distinct geometry is always CPU at width ≤144. [Eligibility][eligibility], [oracle][oracle], [boundary fixture catalog](PRECISION_REPRODUCIBILITY.md#boundary-fixtures-and-routing).

The real near-field recovery test renders ordinary A/Metal, routes near-field B to CPU, then revisits cached A. It establishes that preserved cached Metal remains usable; its final access is not proof of a fresh post-fallback GPU dispatch. The real width 24 silhouette test starts with CPU on an unchecked engine, then performs fresh Metal startup for another eligible request. The scripted precision-domain test also uses a fresh eligible key and checks factory/validation/render counts. [Native routing tests][renderer-tests], [cache tests][cache-tests].

## Cache identity, admission and invalidation

Every key is created only after `scene.validated()` succeeds. Only then are display names replaced with empty strings, preventing invalid metadata from hitting a previously validated frame. Name omission is limited to retained engine cache keys: original, in-flight and UI-held scene snapshots can still contain names. The 80-character validation limit is not a UTF-8 byte bound or constant-time validation guarantee. Identity uses exact scene equality plus effective width and subject; all other values, light order, optics, camera, exposure and room metadata remain. There is no rounded or hash-only identity. A reverted or decoded equal scene may reuse its completed frame; sphere and bust do not share entries. [Engine][engine], [metadata review](workers/w088.md).

Each engine retains at most **4 completed frames, 262144 RGBA bytes and 65536 mask bytes**. [StudyFrameCache][cache] evicts before appending, independently enforces count and both payload budgets, removes an admitted replacement before further eviction, rejects negative or individually oversized costs without disturbing existing entries, and preserves survivor order during selective removal. At 192×128, each frame costs 98304 RGBA and 24576 mask bytes; the limits allow at most two such frames. These are payload accounting facts, not process-memory limits.

New CPU or Metal frames are admitted only after successful rendering and the final cooperative cancellation check. No suspension occurs between that check, insertion and return. Calls that throw cancellation or a rendering error do not admit that call's result; final-check cancellation can discard fully rendered data. A lookup that observes cancellation before promotion leaves LRU order unchanged. An external flag changing after a false final check may still permit successful admission and return. Neither polling nor actor isolation makes cancellation atomic; the caller must still reject an obsolete returned result.

`selectCPU()` replaces the stored backend state with CPU and removes every cached `.metal` frame while preserving completed CPU frames and their relative order. Callback/local references may persist until the call unwinds. This does not revoke images already retained by a caller or another engine. Controlled weak-reference tests observe scripted backend release after the call unwinds while the engine remains alive; their scope is object ownership, not physical GPU/driver memory reclamation. Payload bounds are per engine and exclude caller-held copies, UI storage, allocator overhead, process RSS and driver resources. Resource fixtures intentionally retain returned-frame arrays, so their counters do not demonstrate image-allocation or RSS release.

## Submitted GPU work and caller adoption

Cancellation observed at the pre-submission check prevents commitment; cancellation arriving after that false check may still allow submission. After `commit()`, the code calls `waitUntilCompleted()`, requires command status `.completed`, then checks cancellation, copies shared output into `Data` and constructs the returned `StudyImage` before the `autoreleasepool` returns. Command-status failure is therefore delivered before the post-completion cancellation check. Successful completion followed by observed cancellation throws without returning an image. These are program-order facts; ARC ownership and Metal command-resource retention are separate from measured driver lifetime. No GPU preemption, instantaneous cancellation, bounded GPU completion time or physical resource-release measurement is claimed. The CPU acceptance bound remains at most eight further pixel evaluations after an external cancellation immediately following a false poll; it is not a GPU latency bound. [Engine][engine], [kernel][kernel], [shared math][header], [code acceptance](../../acceptance/m02-m03-code.md).

The actor serializes render calls, not the UI's choice of which completed result is current. A caller must track its active request/generation, invalidate work on edit, subject change, inactivity or disappearance, and recheck cancellation/current identity after awaiting and after image conversion. Image, backend provenance, unsupported-pixel warning and error status must be adopted together. A previous frame may remain visible as previous/updating where appropriate; it must not acquire current backend/status merely because an old scene value reappears.

# Key & Fill prototype privacy and data-handling review

**Draft, updated 2026-11-27.** Not published, legally reviewed, or owner approved. Re-audit the final signed archive, dependencies, actual device behavior, Apple privacy report, and App Store Connect disclosures before release.

## Current implementation

- No app-owned backend, analytics, advertising, account system, tracking, or third-party package dependency in the current prototype. The local Swift package is compiled into the native app.
- Projects and their lighting values, committed measured-room settings and rectangular-emitter roll are stored in the application's Application Support directory. Saved projects contain no reference/test-shot images or undo history. Archived projects remain recoverable; explicitly deleting an archived project removes that record from the current library, not prior exports, OS backups, legacy migration copies, or preserved recovery copies. Platform backup behavior must be reviewed on a real device. No cloud synchronization is implemented by the app.
- Explicit recovery of an unreadable library preserves byte-for-byte copies of its available saved files in a separate local recovery folder before creating a new library. These originals are not sanitized or repaired; they retain whatever data was already in those files. Failed recovery attempts can leave partial preserved copies. The legacy source remains untouched, and deleting a project from the current library does not erase these copies. The app provides no recovery-folder browse, restore or deletion control and does not automatically remove the copies. Their retention and device-backup behavior require review before release. Recovery does not collect reference photos or upload the preserved files.
- The system PhotosPicker supplies user-selected images without requesting broad photo-library access in the current implementation. The system provider may retrieve iCloud-backed photos. The app reads a bounded temporary file, decodes only supported single still images, creates a reduced sRGB derivative, and removes original photo metadata. Generated structural and color-management PNG chunks remain. Sanitized photo copies and analysis summaries remain in memory for their reference or test-shot comparison session. Cancelling or failing a replacement preserves the previous photo and guided work. Nested pickers/sheets and cancelled dismissal gestures retain the underlying session; explicit Remove/Clear, completed dismissal, terminal view removal, or successfully applying a reference rig releases the relevant session's app references. A comparison seeded from Reference holds its own reference, so clearing one session does not clear the other. Photos are hidden while the scene is inactive. Actual picker behavior, inactive snapshots, cancellation and retention still require physical-device verification; this is not a secure-memory-erasure claim.
- Reference analysis uses Apple Vision on device to detect face bounds and pose, then compares pixel brightness to propose a possible brighter/key side. It performs no identity recognition or remote inference. Analysis pixels and Vision observations are released after the request; session results are not saved with projects. These are editable lighting proposals, not identification or exact lighting reconstruction. See `ReferenceAnalysisService` and `ReferenceComparisonView`.
- PDF and text exports are generated locally and contain scene data, not reference photos. The system share action is user-initiated; the chosen destination can retain the exported copy. The app cannot delete copies a recipient or another app owns.
- Editable project backups contain the project name and scene settings, including committed measured-room settings, rectangular-emitter roll and the scene's per-light UUIDs for editable light identity. They omit the project-library record ID, active/archive state, reference/test-shot photos and edit history. Project and light names remain user-entered content. The user chooses a destination through the system file exporter. Import reads only a user-selected JSON file, holds security-scoped access during coordinated bounded reads, validates the document, then creates a separate project with a fresh project ID through the existing conflict-checked store. A selected file provider may download or retain files according to its own settings. Actual provider, cancellation and device behavior remain unverified.
- Room measurement notes are a separate, user-initiated text export of the committed room dimensions, subject offsets, rig rotation, equipment names and calculated placement/footprint warnings. The preview and system share action use the same immutable text. These notes contain no reference image, source photo metadata, source URL, project-library identity or undo history. Closing the room view does not remove copies already shared to another destination.
- Photo and editable-project file reads share `BoundedFileReader`: the no-follow/nonblocking open and `fstat` check validate the actual opened descriptor, reject nonregular files and a final symbolic link, bound actual bytes, and check cancellation. The respective 32 MiB photo and 8 MiB project limits do not rely solely on earlier pathname metadata. For editable-project imports, `ProjectDocumentIO` first requests final-path metadata through `lstat` while security scope is held and before file coordination. This preflight rejects known nonregular items without opening or reading their contents; unavailable metadata is left to the coordinator/provider. A successful preflight neither grants access nor proves the identity of a later file. The authoritative descriptor checks still run inside the coordinated accessor. Actual provider behavior and resolution of the observed native import stall require current native verification.
- AR placement requests camera permission only after the user chooses Start AR camera. Camera frames and tracking/world maps are not persisted or sent to another service by the app. The camera session stops and placement anchors clear when the active session becomes inactive or the view is dismissed; restarting requires an explicit start. AR uses live tracking to place the authored rig, not a saved room scan. See `ARPlacementController` and `ARPlacementView`; verify permission and lifecycle behavior on device.
- Measurement-unit, appearance and welcome-dismissal preferences persist in the app's `UserDefaults` through `StudioPreferences`. They contain no photo, feedback-note or purchase entitlement data.
- Beta feedback contains optional notes entered by the user plus app version/build, OS version and a coarse device family. When a build records a valid source revision, the reviewed report also includes that public code revision to identify the build; it is not a user, account, device or session identifier. Drafts and the reviewed report remain in memory while the feedback sheet is open; closing a populated draft asks whether to discard it. The app adds no photographs, project or scene contents, account details, network or hardware identifiers, or logs. User-entered private information is not automatically redacted. Review shows the exact text passed to the user-initiated system share action; the user chooses the destination or cancels. Nothing is sent automatically, and previously shared copies remain under the destination's control.
- Optional StoreKit support checks verified transactions for the configured non-consumable product. An absent, blank or unresolved `KEYFILL_PRO_PRODUCT_ID` disables sales; there is no fallback SKU or hardcoded price. Displayed pricing comes from StoreKit. Launch/foreground entitlement refresh does not automatically invoke Restore Purchases; `AppStore.sync()` runs only from an explicit restore action and may require Apple authentication. Product lookup, purchases and restoration can contact Apple services. See `EntitlementStore`; actual product configuration and transaction behavior remain release-review items.
- Each configured purchase attempt sends a fresh random UUID to Apple as its `appAccountToken`, so a verified transaction can be correlated with that pending attempt. This is an attempt identifier, not an app account or device identifier. StoreKit transactions can contain the token; the app holds its current attempt state only in memory and does not add the token to project files, preferences, feedback or diagnostics. Actual StoreKit transaction and retention behavior remains subject to the configured sandbox/device review.
- Input diagnostics exist only in `#if DEBUG` builds and require the explicit `KEYFILL_UI_TEXT_INPUT_TRACE=1` launch environment value. The shared recorder emits at most 512 records per process and 256 per control to app stdout and unified logging; developer CI may retain these logs as test artifacts. Records contain event order, wall-clock time, temporary control/lifecycle identifiers, allowlisted field names, bounded lengths and state flags. They contain no raw typed text, arbitrary labels/identifiers or system uptime. Event sequence preserves ordering when the wall clock changes. These diagnostics are separate from the user feedback report and must remain excluded from the signed Release build.
- Separate DEBUG layout probes require `-ui-testing` and `KEYFILL_UI_TEXT_LAYOUT_PROBES=1`; they expose fixed probe names and geometry through accessibility values. DEBUG slider logging requires `-ui-testing` and `KEYFILL_UI_TEST_SLIDER_TRACE=1`, and records fixed control identifiers, numeric display/model values and interaction state in unified logging. This slider path is capped at 64 records per native slider object, with no process-wide cap. These switches and limits are distinct from the shared text recorder above; CI can retain the resulting logs. Slider logging and layout observation are inactive in Release, and none of these diagnostics is attached to beta feedback.


## Privacy manifest and required reasons

Apple documentation references for release review:

- [Required-reason API categories and approved reasons](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype)
- [Describing use of required reason API](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api)
- [Photos picker selection and provider retrieval](https://developer.apple.com/documentation/photokit/selecting-photos-and-videos-in-ios)

The source manifest declares no tracking or data collection by the app. This declaration is not final approval of App Store privacy claims. Its required-reason categories document these scoped purposes:

| Reason | Current purpose | Source |
| --- | --- | --- |
| CA92.1 (UserDefaults) | Persist the app's measurement-unit, appearance and welcome-dismissal preferences. | StudioPreferences; StudioWelcomeView; Resources/PrivacyInfo.xcprivacy |
| C617.1 | Determine type and size of local sandbox project files before bounded reads. | SceneFileStore, ProjectLibraryFileStore, ProjectStore |
| 3B52.1 | Reject known nonregular selected project paths before coordination; determine the actual opened file type and size for explicitly selected photo or editable-project files before bounded reads. | BoundedFileReader: Darwin.lstat for the metadata-only ProjectDocumentIO preflight, Darwin.fstat for actual photo/project reads; selection through PhotosPicker or fileImporter |

The existing C617.1 and 3B52.1 declarations remain unchanged. Apple lists `fstat` in the file-timestamp API category even though this helper uses only file type and size. The added `lstat` preflight uses metadata only to reject a known nonregular selected item; it does not replace the opened-descriptor protections or introduce a new data-collection purpose. No file timestamp or filesystem metadata is uploaded or used for tracking by these paths. The source audit is not a binary API-symbol audit. The build check verifies plist structure and actual resource inclusion; it cannot prove runtime privacy, permission behavior, or compliance. Obtain device and signed archive evidence before passing the privacy gate. The [native import repair report](evidence/2026-11-24-autonomous/native-import-stall.md) preserves the observed stall, implemented ordering correction and remaining Apple/provider acceptance.

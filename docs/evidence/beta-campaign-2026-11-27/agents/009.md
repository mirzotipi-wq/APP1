## Findings

1. Healthy current-format libraries and valid migratable legacy scenes do not authorize recovery. Inspection calls the same decode/validation logic without the normal loader's migration write. Existing load/save/migration code is unchanged. Recovery validates and encodes its replacement before storage mutations, uses the existing shared lock, compares complete observations twice, and rejects changed bytes, presence or recorded file identity before replacement.
2. Read, permission and other filesystem failures cannot become a decode-failure token: snapshot construction must succeed before eligibility is tested. Missing files alone are ineligible. Both metadata size and actual reads are bounded to 8 MiB/1 MiB. Direct source/store symlinks and nonregular files are rejected; a symlinked archive root is rejected.
3. Archival writes original filenames and exact observed bytes without overwriting, synchronizes each file, and reads it back before the final atomic library write. Legacy bytes remain untouched. Archive failures precede replacement, and partial evidence is deliberately retained. Fixed recovery errors avoid exposing private filesystem paths.
4. **Eligibility scope:** `ProjectLibrary.swift:327–338` catches every decode/validation error, including unsupported library/scene versions. Eligibility means “cannot be opened by this app version,” not necessarily corruption. The UI must use that distinction; a corruption-only product policy would require excluding unsupported-version failures.
5. **Identity scope:** the snapshot binds a standardized directory pathname and source-file identities; it does not record the parent directory's inode or reject symlinked ancestors. The tests establish direct-symlink behavior, not arbitrary directory-topology protection. Concurrent direct filesystem writers are explicitly outside the existing contract.

## Findings

The actual limit is consistently twelve: `LightingScene.validated()` rejects thirteen, `SceneLightCreation.addingLight` validates both source and result and rejects capacity, both Add controls disable at twelve, and Duplicate has both the UI disablement and command guard. The inspector remains available for existing lights. Busy/readiness/generation protection ultimately reaches `StudioSession.allowsMutation`; UI disablement is not the sole validation boundary.

Add chooses the first unused exact `Light N` name. Duplicating uses the captured live UUID, supplies a new UUID, finds an unused suffix, bounds imported display text before appending that suffix, and retains all equipment geometry/settings. UUID creation is intentionally random; naming is deterministic for the same existing names. The executable probe exercised eleven consecutive duplicates, including 80-character ASCII, 80 joined-family emoji, a 4,096-combining-mark grapheme, an invisible imported name and ordinary names. Every generated duplicate name passed all new-input limits, while the original imported name was preserved. Names `Light 1` through `Light 11` produced `Light 12`.

Removal uses the confirmation's captured UUID and generation. Missing targets produce an unchanged candidate. `StudioEditorState.replace` validates before recording history; rejected duplicate UUIDs, thirteen-light scenes and invalid intensities preserved the complete editor, including selection, revision and a usable redo branch. Valid 100,000 cd / 20,000 K values survived duplication unchanged.

Undo/redo stores full scenes. The probe verified exact sorted-JSON scene restoration with lens, preview, measured room, manual aim, emitter dimensions/roll and UUIDs present. Removing the selected light selects the first remaining UUID; undo retains that still-valid selection, as DESIGN requires. Empty rigs clear selection; restoring from empty selects the first light.

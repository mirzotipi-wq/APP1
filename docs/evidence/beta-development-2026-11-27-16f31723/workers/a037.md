`App/BoundedFileReader.swift:16–28` treats pathname preflight as advisory. The actual open uses `O_NOFOLLOW`, `O_NONBLOCK` and `O_CLOEXEC`; `fstat` then verifies the opened object is a regular file before reading (`36–63`). Final symlinks are rejected, FIFOs cannot block the open, and replacing a pathname after open cannot redirect its descriptor. This is final-component validation, not a directory-confinement claim.

The nonnegative, strictly-below-`Int.max` limit prevents `maximumBytes + 1` overflow. Each read is at most 64 KiB and remaining capacity plus one probe byte, so post-stat growth cannot return oversized data (`63–76`). Truncation may yield shorter bytes; the reader does not promise an atomic snapshot, and callers still validate document/image decoding. Production callers supply fixed 8 MiB project and 32 MiB photo limits.

Every successful open immediately acquires a `FileHandle` with both deferred close and deallocation ownership (`54–55`). Every later return or throw crosses that cleanup. Actual task cancellation cannot be suppressed by the caller checkpoint; checks precede open, each chunk and final delivery. Cancellation never returns partial data.

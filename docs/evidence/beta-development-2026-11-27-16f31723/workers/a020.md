## Disposition

`StudyRenderEngine.render` is an actor-isolated synchronous method with no suspension (`App/MetalStudyRenderer.swift:224–287`). A and B cannot interleave backend initialization, rendering or cache admission. A cancelled caller queued behind another request throws at entry; an already-running CPU render checks cancellation before each block of at most eight pixel evaluations and before returning. Final engine checks precede cache admission. Completed valid frames can remain reusable; the caller separately decides whether to adopt them.

Submitted Metal work waits for its command to finish before releasing buffers (`:107–114`). Consequently a later caller may wait for that one submitted command; cancellation does not promise immediate GPU preemption or a wall-clock deadline. This is intentional resource-lifetime behavior, not evidence of a deadlock. No actor lock or continuation is stranded by an error.

Confirmed command/allocation/malformed-output failures call `selectCPU` before observing concurrent cancellation. That transition evicts all Metal frames (`:290–295`); ordinary cancellation or precision-domain routing does not disable a valid backend. In A→B→A, each activation reconsults the engine, while `StudyPreviewPipeline` checks ticket and task cancellation before conversion and publication (`App/ReferenceStudyPreview.swift:24–55, 215–236`). Late B results cannot overwrite newer A.

Existing tests cover concurrent initialization, actual task cancellation, cancellation during validation, no cache retention for cancelled renders, failure-plus-cancellation downgrade, noncooperative late success/failure, and hosted A→B→A adoption after downgrade. These are relevant source checks; their execution is not claimed.

## Challenge and result

Existing tests separately cover committed first-save cancellation, observer lifetime, project switching and stale-save recovery. This independent probe combined those boundaries around a real **metadata rename or duplicate commit**:

1. Window A committed the library command, then paused delivery of its receipt.
2. Window B loaded that committed library, changed the active scene and saved it.
3. A's observer or session task was cancelled before receipt delivery.
4. A settled its matching receipt, made a new local edit, attempted a stale save and recovered its draft as a separate project.

All **four interleavings and 130 invariant checks passed** against the actual compiled `StudioComposition` and `LightingCore` objects, using real temporary library files. Cancellation did not abandon the committed reservation. Receipt adoption did not rewrite B's newer bytes. Rename retained the document/presentation identity; duplicate changed it and rejected old callbacks. Re-reading a task result did not re-adopt. The subsequent stale save preserved A's scene/history and dirty/conflict state while leaving B's bytes unchanged. Recovery appended once and retained both windows' scenes. All settled and failed operations released busy/task state.

## Source reasoning

`ProjectStore.perform` checks cancellation before synchronous work and returns committed receipts without a post-commit cancellation throw. `StudioSession` owns an unstructured task, reserves synchronously and reconciles the receipt independently of a sheet observer. Pending operations reject mutations and further reservations. Adoption requires matching request, generation and current project identity; task cleanup additionally checks its request ID. Scene/history validation occurs before publishing adoption. Saved metadata receipts retain current scene/history; explicit project changes reset presentation.

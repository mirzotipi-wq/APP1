# Worker a004 — bounded study render reuse

## Scope and baseline

Distinct worker 4. Initial HEAD was `7dca1b0`; root subsequently published `cebb259` without changing the owned renderer. Read the repository directive, operating protocol, current handoff/state, product, architecture, roadmap, quality and design contracts, both renderers, input validation, Float32 eligibility and existing native renderer tests. Existing unrelated changes were preserved. Root owns integration and runtime verification. No subagents, builds, commits or pushes were performed.

Problem: returning to completed settings or reopening a scene reran successful CPU/Metal work after the view's single retained frame was replaced. Hypothesis: actor-local reuse of validated successful results can remove that work while preserving pixels, errors, cancellation and backend routing. Acceptance: deterministic cache-hit/eviction/cancellation tests plus unchanged renderer parity/routing tests, with native execution by root. No physical performance claim is made.

## Changes

- `App/MetalStudyRenderer.swift`: least-recently-used result cache inside the existing shared render actor, limited to four frames and 256 KiB of retained RGBA bytes. Eviction precedes admission. At maximum sphere resolution this retains at most two frames. Keys retain no arbitrary-length display names and contain at most twelve validated lights; numeric/UUID key storage is separately bounded by that count.
- Cache keys compare complete scene values except validated display names, plus study subject and the renderer's effective width. Complete camera, optics, exposure, light ordering, identity, schema and room values remain represented. No quantization or hash-only identity. Bust width still uses the existing 144-pixel clamp.
- Scene validation occurs before lookup; invalid requests continue through existing render branches and preserve their original error ordering. This includes invalid names, duplicate IDs, schema violations, legacy scenes carrying measured rooms and malformed settings.
- Cancellation is checked before lookup and again before a hit returns or changes recency. Admission occurs only after the existing final cancellation check, with no actor suspension before return. Cancelled/failed work never reaches admission. Actual task cancellation remains combined with the optional cooperative predicate.
- Backend failures retain the existing CPU fallback and also discard old Metal frames, preventing a later hit from restoring a failed backend. Per-scene precision routing does not downgrade the backend or discard successful CPU frames.
- `NativeTests/StudyRenderCacheTests.swift`: eleven native tests cover revert/reopen hits with exact CPU pixels, LRU eviction, byte-budget eviction, fifteen rendering-control changes, subject/resolution identity, bust clamping, invalid metadata and error ordering, cancellation before/after lookup, actual task cancellation, interrupted CPU work and cancellation after CPU completion.

The tests use a cancellation budget: a real 24 × 16 CPU render requires at least 48 pixel checks, so eight checks admit a hit while interrupting recomputation. Large-frame eviction uses far-camera geometry that deterministically routes to CPU. No timing benchmarks, fake renderer or production test counters were added.

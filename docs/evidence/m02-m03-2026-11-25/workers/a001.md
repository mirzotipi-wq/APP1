## Prioritized implementation packets

### 1. Bounded reuse of completed diagnostic renders — useful M02 performance work

**Targets:** `App/MetalStudyRenderer.swift` (`StudyRenderEngine`, lines 123–183); `App/ReferenceStudyPreview.swift` (`Request`, lines 13–25, task lines 105–130); `NativeTests/StudyRendererTests.swift`. A small portable render-key type and tests can live in LightingCore if that makes identity independently testable.

**Observed gap:** The shared engine retains the Metal pipeline/backend but no rendered frames. The view retains only one frame for its own lifetime. Re-entering Study after another mode, alternating sphere/bust, or undoing to an earlier lighting setup recomputes pixels. Render request equality includes nonvisual scene metadata; the view already strips measured-room settings, but light names/identities can still trigger unnecessary rendering. The bust path is CPU-only, with up to 144×96 pixels and repeated finite-emitter/mesh work.

**Bounded implementation:** Add an actor-owned, explicitly memory-bounded LRU of successful frames (e.g. four entries and a byte cap). Define rendering identity from the actual scene inputs, subject and width; strip only fields demonstrably unused by pixels. Validate source before any cache hit so metadata normalization cannot bypass existing invalid-input rejection. Preserve explicit width validation, precision routing, runtime backend validation, cancellation and CPU fallback. Do not cache failures or a canceled result. Retain honest backend metadata. Avoid rasterizing previews on the main actor.

**Acceptance:** Identical and A→B→A requests reuse the completed result; lighting/camera/lens/exposure/white-balance/subject/size changes miss; metadata-only changes hit where permitted; canceled or invalid work never becomes a hit; capacity evicts the least recently used entry; returned pixels equal the original uncached path. Measure repeated-request cost on the same workload and distinguish this from device frame-rate acceptance. This does not make the CPU mannequin a real-time renderer or pass the physical performance gate.

### 3. Align the SceneKit modifier face with authored geometry — concrete M02 accuracy correction

**Targets:** `App/SpatialPreview.swift`, `populate` lines 263–315; `NativeTests/SpatialPreviewTests.swift`. Compare `App/StudioEntityGraph.swift` lines 263–268 as the correct existing convention.

**Observed discrepancy:** SceneKit constructs a rectangular housing as an `SCNBox` of depth 0.055 centered at `light.position` (lines 287–290), while its source is also at `light.position`. The forward housing face therefore lies 0.0275 m ahead of the authored emitting plane. RealityKit explicitly places its housing behind the plane and its diffuser at local z=0. Plan/room calculations also treat the authored position as the ideal emitting face. This is a source-demonstrable geometry inconsistency, not a claimed measured photometric error.

**Bounded implementation:** Use a root at the authored source, with the housing offset behind the emitting face and a separate diffuser at the plane. Apply the shared frame/roll once. Preserve stable selection mapping for the housing/stand and exact width/height. Do not change light intensity mapping or claim calibrated shading.

**Acceptance:** In ordinary, rolled and vertical-aim cases the world diffuser corners match `EmitterFrame`/room-plan geometry; front plane lies at the authored position; selection still finds the source; translated rig fit remains valid; no duplicate/copolanar faces. Native projection tests are appropriate, followed by a screenshot of an oblique rectangular emitter.

**Acceptance:** Translated and rotated rigs receive the intended relative position; existing lights/aims/room/camera are unchanged; outside-domain insertion is atomic; add→Undo→Redo→save/relaunch retains identity and exact coordinates.

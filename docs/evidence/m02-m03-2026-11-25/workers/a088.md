The whole plan is inside `StudioView.workspace`'s fixed 280-point height and rounded clipping shape.

The source has two independent font-resolution paths: the SwiftUI semantic Text font and an explicitly constructed UIKit font. No larger-category screenshot or measurement is exported here, so this evidence establishes the constrained bounds and source risk; it does **not** prove the precise category where they diverge. The default Subject crop is visibly complete. The issue description specifically says it may clip at larger Dynamic Type sizes.

**Concrete repair candidate for captions:** retain semantic fonts; measure a preferred caption font for the explicitly mapped current `DynamicTypeSize`/UIKit content-size traits, matching the rendering weight/design. Remove the exact Text height and let its intrinsic height grow. Permit wrapping within a width that can increase with the available canvas, and measure the same multiline constraint for collision placement. The existing unscaled 128-point cap and `.lineLimit(1)` cannot guarantee readable large text. Preserve the bounded input-name sanitizer, marker anchor positions, gesture callbacks, 44-point controls, and the collision solver's ordering.

For accessibility sizes or an unplaceable full caption, provide a visible naturally sized legend adjacent to the canvas; it must retain the equipment name and the corresponding selection/edit action. A caption that disappears with no equivalent visible content is not a scaling fix. Avoid restoring `.accessibilityHidden(true)` on visible captions.

**Concrete repair candidate for the grid title:** move the same title into a naturally sizing header immediately above the fixed diagram, or give it a genuine wrapping/intrinsic-height allocation and reserve precisely that height in caption placement. Keep the spacing value/unit visible and accessible. This prevents a text header from competing with the fixed graphical canvas's height. The baseline already uses `.caption2.monospaced().weight(.medium)`; replacing it with another semantic-font spelling alone does not address a demonstrated constraint.

Apple documents preferred UIFont creation with explicit compatible traits and notes that font metrics can vary with language/device settings: [preferredFont(forTextStyle:compatibleWith:)](https://developer.apple.com/documentation/uikit/uifont/preferredfont%28fortextstyle%3Acompatiblewith%3A%29). Its accessibility guidance explains that fixed text containers can clip Dynamic Type and recommends adapting layout to retain readable content: [Get started with Dynamic Type, WWDC24](https://developer.apple.com/videos/play/wwdc2024/10074/). These support the implementation direction; they do not establish that this candidate passes.

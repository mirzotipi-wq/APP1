# a051 — atomic persistence paths

Reviewed HEAD `90d36f9120289a33ff8af37d626ea959830ddd38`, `AGENTS.md` and `m02-m03-code-v2`. M03 preparation only; no acceptance promotion. Relevant production files have no working-tree diff.

**Source findings:** `ProjectLibraryFileStore.save(_:replacing:)` validates the candidate, then holds its process-wide lock through existing-snapshot validation/comparison and replacement. `write(_:)` encodes and enforces 8 MiB before directory creation or `.atomic` writing. Recovery edits remain local until that write succeeds. `loadWhileLocked()` can intentionally migrate missing-library legacy data; it never falls back over a malformed existing library.

`SceneFileStore.save(_:)` first loads/protects existing data, then `SceneCodec.encode(_:)` validates and enforces 1 MiB before creating parent directories and writing atomically. Missing parents permit first save; inaccessible, malformed, oversized and nonregular existing targets propagate errors. Directory creation may leave new empty directories on failure, but does not truncate existing JSON. This legacy store does not provide the library's concurrent-writer CAS contract.

`ProjectStore.perform(_:)` checks cancellation before synchronous work and returns the saved snapshot only after success, without postcommit cancellation. Production errors propagate; swallowed catches are DEBUG fixture preparation only. `ProjectLibraryOperationState.adopt` guards pending request, generation and current project identity, preserves newer unsaved scenes, and consumes successful receipts once.

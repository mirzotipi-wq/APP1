## Findings

No concrete replacement/data-loss counterexample found in the inspected source.

- `ProjectLibrary.maximumProjects` is 64. The replacement transaction loads and validates the latest library under the process-wide lock. At capacity it compares the complete observed candidate, requires archived/inactive status, removes only that record, creates one recovery record, and writes atomically. Changed, restored or removed candidates fail closed before writing.
- If capacity opens between offer and confirmation, the transaction appends without deleting or requiring the old candidate to remain eligible. This is intentional nondestructive recovery, including an active selected record. Unrelated newer records retain their identity/content/order. The previous active record is preserved, while `activeID` intentionally becomes the new recovery ID; it is not an invariant that the old active ID remains selected.
- `RecoveryCapacityView` computes name/ID disambiguation from all validated records before filtering archives. Validation excludes an archived active record. Selection freezes the complete displayed record. Confirmation names it, explains irreversible removal, and explicitly conditions removal on capacity still being full.
- Loading/replacing prevents candidate interaction; replacement disables Keep editing and interactive dismissal. Reload invalidates prior selection/request; asynchronous failure reloads choices without adopting them over unsaved edits.

## Findings

- `SceneLightCreation.addingLight(to:id:)` validates before/after creation, refuses a thirteenth light, and rejects injected duplicate UUIDs. `SceneLightCreationTests.testBoundaryCapacityAndDuplicateIdentityFailWithoutChangingSource` covers those boundaries. Placement preserves existing lights; its history test checks exact scene/identity restoration.
- `StudioView.duplicateLight(_:)` copies the entire `StudioLight`, changing only UUID/name, preserving position, candela, kelvin and optional optics. Both UI and callback cap count at twelve; `replace(_:)` validates uniqueness before adoption. Name suffixing uses bounded `StudioDisplayName` output plus `newInput` validation, including scalar-heavy graphemes.
- `StudioDisplayName.newInput`, `display`, and `label` bound character/scalar/UTF-8 size; existing tests cover joined emoji, natural RTL, bidi/control sanitization, invisible names, pathological graphemes, exact limits and retained legacy data.
- Add/duplicate select the new UUID. Removal captures UUID/generation. `repairSelection`, `undo`, and `redo` preserve the current selected UUID when valid, otherwise choose the first remaining UUID (or nil). This matches the requested selection policy.
- `control` and `opticsBinding(for:)` capture UUID and project generation, then resolve the current index; removed IDs are ignored and callbacks cannot redirect to another selected light. Owner-qualified history tests cover delayed endings.

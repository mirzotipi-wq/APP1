## Finding

**No concrete correctness regression found in the current scene-phase change.** This is source review and Linux syntax validation, not an Apple build or lifecycle execution.

- **Cancellation:** `App/ReferenceStudyPreview.swift`, `activeRequest` and `.task(id: activeRequest)`, map every non-active phase to `nil`. An observed active-to-inactive transition changes task identity, cancelling the previous task; the new nil task returns without rendering. The 80 ms debounce exits on cancellation. The renderer runs in the same task across the actor hop, so `StudyRenderEngine.render` observes `Task.isCancelled`; there is no detached task that loses this cancellation state.
- **Stale publication:** after the engine call, the preview checks cancellation before and after `makeImage`; its error branch rejects actual task cancellation, `CancellationError`, and `StudyError.cancelled`. There is no suspension between the final success guard and `frame` assignment, or between the error guard and its assignment. Therefore a cancelled earlier request cannot resume past those guards and publish a success/error into the view. This reasoning assumes SwiftUI's task cancellation and main-actor scheduling contract; it does not claim cancellation can interrupt arbitrary synchronous instructions.
- **Resume:** inactive-to-active changes nil to the latest scene/subject request, even when scene edits occurred while all inactive task IDs stayed nil. A completed matching image is intentionally reused. Interrupted or failed work remains retryable because the early return requires `frame.image != nil`. `StudyRenderEngine` leaves initial backend validation `.unchecked` when cancellation interrupts it, so foreground recovery can retry validation rather than permanently select CPU.
- **Identity:** `Request.init` removes only `placementRoom`, which does not affect this study, and retains scene optics, camera, preview settings and subject. `Frame.request` is the task's captured snapshot. A prior same-subject success may remain visible, but the body marks it `studyPreviousPreview` and exposes updating status; a different subject or old error cannot masquerade as the current frame. Rapid A→B→A can reuse a completed A while cancellation prevents B from overwriting it.
- **Actor boundary:** the task closure is declared inside SwiftUI `body` and inherits its main-actor context. `frame` reads/writes and `makeImage` remain there, while the actor-isolated synchronous renderer performs CPU/GPU work on `StudyRenderEngine`. The synchronous renderer has no actor-reentrancy suspension. The phase addition introduces no new actor crossing. Apple SDK type checking was unavailable, so this is not a compiler-proven isolation result.

`App/MetalStudyRenderer.swift` permits already-submitted GPU commands to finish, checks cancellation before retaining results, and uses CPU pixel checkpoints. Its concurrent `StudyFrameCache` extraction was also inspected: cancellation remains checked before lookup promotion and before result admission; backend downgrade still removes Metal frames. This review does not infer instant GPU interruption or device background execution performance.
